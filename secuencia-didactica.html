Secuencia Didáctica · Desarrollo Web con IA

Universidad Tecnológica de Ciudad Juárez · {Carrera: Ingeniería en Tecnologías de la Información / Desarrollo de Software} · 3er Cuatrimestre · Grupo: ______ · Docente: ______ · Ciclo: ______

Unidad didácticaConstrucción de una aplicación web real: sitio profesional de asesorías con asistente de IA, ruta de WhatsApp y pruebas automáticas (caso de estudio: sitio de Laura, asesorías de artículos científicos).
Duración8 sesiones de 120–150 min (≈ 16–20 hrs). Cada sesión entrega una evidencia con rúbrica SEET.
EnfoqueClases guiadas: CodeAlong del maestro → práctica en parejas (maestro-alumno) → reto individual → entrega de evidencia.
GamificaciónXP por evidencias, "jefes finales" semanales y Demo Day. Los puntos se registran en la bitácora del grupo.
Competencias• Diseñar interfaces web con HTML5 semántico y CSS moderno (Flexbox/Grid, variables, responsive).
• Programar lógica en JavaScript moderno (ES6+, DOM, asincronía).
• Tipar y estructurar proyectos con TypeScript y npm/bun + Git.
• Construir interfaces reactivas con React (componentes, props, estado, hooks) y Radix/shadcn + Tailwind.
• Integrar datos: rutas, API REST, validación con esquemas.
• Consumir IA generativa (chatbot con API) y probar código con Vitest.
• Documentar, versionar y desplegar proyectos.
Evidencia centralE8 — Mini SaaS propio: el alumno replica la arquitectura del sitio (landing + chatbot propio + ruta de contacto + pruebas), con datos reales de un negocio local. Esta es la evidencia integradora del cuatrimestre.
¿Por qué este contenido es "actual y retador"? Los alumnos construyen una aplicación que existe y está en producción: el asistente de IA del sitio responde solo con información confirmada, genera un resumen de la consulta y lo envía por WhatsApp. Cada sesión introduce una pieza real de esa app (HTML → CSS → JS → TS → React → API → IA → pruebas → deploy), por lo que el aprendizaje es incremental, verificable y con propósito: un producto, no ejercicios sueltos.

1. Plan de las 8 sesiones (120–150 min c/u)

Sesión 1 · HTML5 semántico + CSS moderno · La base del sitio130 min
Aprendizaje esperado: Maquetar una landing page accesible y responsive con HTML semántico y CSS (variables, Flexbox, Grid, media queries). Reto: "Landing page de Laura" — secciones: hero, servicios, artículos científicos, contacto (WhatsApp), footer.
0–10Inicio: bitácora XP, repaso de retos anteriores, " ¿Qué haría un buen landing de asesorías?" (lluvia de ideas).
10–35CodeAlong maestro: estructura HTML5 semántica (<header>, <main>, <section>, <article>, <nav>, <footer>, aria-labels) inspeccionando la página real del sitio.
35–70CodeAlong CSS: variables CSS, Flexbox/Grid, hover states, media queries responsive (móvil primero).
70–105Práctica maestro-alumno: parejas replican la landing en VS Code, rota el "driver/navigator" cada 10 min. Desafío extra: modo oscuro con variables.
105–125Reto individual (15 min): maquetar sección "Artículos científicos" con tarjetas responsive sin copiar.
125–130Cierre: entrega E1 + retroalimentación rápida (2 estrellas, 1 mejora).
Evidencia E1: Landing page HTML+CSS responsive (archivo único o carpeta), subida a GitHub Pages/Replit/Netlify Drop. XP: 100
Sesión 2 · JavaScript moderno · El cerebro del orientador140 min
Aprendizaje esperado: ES6+: arrow functions, destructuring, spread, template literals, arrays/objetos, DOM, eventos, asincronía (promesas, async/await, fetch). Reto: "Mini orientador" — script que simula el chat: responde con datos confirmados y arma un resumen de la consulta (igual que orientador.server.ts lo hace en producción).
0–15Inicio: Kahoot/quiz relámpago (10 preguntas JS). Bitácora XP.
15–50CodeAlong: datos confirmados como array de constantes (ver asesorias-info.ts), funciones puras, template literals, manejo del DOM (input + botón + lista de mensajes).
50–80CodeAlong: asincronía — fetch a una API pública (ej. API de país o placeholder), async/await, manejo de errores.
80–115Práctica maestro-alumno en trios: construyen el mini chat. Roles: 1 escribe, 1 revisa con rúbrica de "código limpio", 1 documenta decisiones.
115–135Reto individual: agregar validación (si el input está vacío, alerta amigable) y un botón "Limpiar chat".
135–140Cierre: demo de 2 parejas + entrega E2.
Evidencia E2: Mini chat JS funcional + captura de consola limpia + URL pública. XP: 150
Sesión 3 · Git + Node/bun + estructura profesional · El taller del dev130 min
Aprendizaje esperado: Git/GitHub (init, commit, push, ramas), gestores de paquetes (npm/bun), package.json, scripts (dev, build), estructura de carpetas src/, linters. Reto: "Fork & Fix" — cada alumno clona un repo con errores intencionales y lo deja verde.
0–15Inicio: reto sorpresa — el maestro rompe algo en pantalla y los alumnos diagnostican (git status/log).
15–50CodeAlong: git init/add/commit/push, .gitignore, repo en GitHub, GitHub Pages. Luego npm init/bun init, instalar dependencias (vite, typescript), scripts en package.json.
50–80CodeAlong: vite dev server, entrada index.html → src/main.ts(x), primera pantalla renderizada.
80–115Práctica maestro-alumno: parejas clonan el "repo roto" del maestro (5 bugs marcados con TODO), cada uno resuelve 1–2 y hace PR con descripción.
115–125Mini-reto: crear su propio repo del proyecto del cuatrimestre ("Sitio [Negocio]").
125–130Cierre: entrega E3 (link al repo con historial de commits).
Evidencia E3: Repo propio en GitHub con ≥5 commits, package.json y README con instrucciones de instalación. XP: 150
Sesión 4 · TypeScript · Tipos que salvan vidas140 min
Aprendizaje esperado: Tipos primitivos, interfaces, type aliases, union types, generics básicos, strict mode, inferencia, errores de compilación como guía. Reto: "TS Challenge" — el código JS de la sesión 2 se migra a TS; el compilador "castiga" los errores.
0–15Inicio: comparación en vivo — mismo código en JS vs TS (el TS "detecta" bugs antes de correr).
15–55CodeAlong: tsconfig.json strict, interfaces para Mensaje, Usuario, ResumenConsulta (ver resumen.ts); tipos para props y funciones.
55–80CodeAlong: generics simples (Array<T>, función fetchJson<T>), union types, optional chaining.
80–115Práctica maestro-alumno: migración guiada del mini chat a TS. Reto oculto: función con error de tipo que debe descubrirse vía compilador.
115–135Reto individual: tipar el objeto "negocio" de su proyecto (nombre, WhatsApp, servicios, horarios...).
135–140Cierre: entrega E4 (repo con código TS compilando sin errores, tsc --noEmit en verde).
Evidencia E4: Código TS migrado + captura de compilación exitosa + 3 interfaces propias documentadas. XP: 150
Sesión 5 · React I · Componentes, props y estado · La UI cobra vida150 min
Aprendizaje esperado: JSX, componentes funcionales, props, useState, useEffect, listas con .map() + keys, formularios controlados. Reto: Convertir la landing de HTML en componentes React reutilizables (Header, Hero, CardServicio, Footer... como en src/components del sitio real).
0–15Inicio: "¿Por qué React?" — render declarativo vs manipular DOM a mano. Mini demo del sitio real.
15–55CodeAlong: crear app React (Vite), JSX, primer componente, props tipadas con TS, composición.
55–85CodeAlong: useState (contador → tema claro/oscuro), useEffect (localStorage, fetch), listas dinámicas, formulario controlado de "contacto".
85–125Práctica maestro-alumno: trios convierten la landing E1 en componentes React. Cada uno es "dueño" de 2 componentes; deben integrarlos.
125–145Reto individual: agregar un componente ContadorXP interactivo (sumar puntos por actividad).
145–150Cierre: entrega E5.
Evidencia E5: App React con ≥6 componentes propios, estado interactivo y deploy. XP: 200
Sesión 6 · React II + Radix/shadcn + Tailwind · UI profesional y accesible140 min
Aprendizaje esperado: Tailwind utility-first, diseño responsive, shadcn/ui (componentes sobre Radix), accesibilidad (roles, focus, aria), diseño de sistemas. Reto: "Skins challenge" — el mismo componente con 3 temas visuales (claro/oscuro/neón).
0–15Inicio: inspección del sitio real — "¿de dónde salen estos componentes tan bonitos?" (shadcn/Radix).
15–50CodeAlong: instalar Tailwind, utilities, breakpoints, custom config; agregar shadcn components (button, card, dialog, accordion) y analizar un componente Radix por dentro.
50–75CodeAlong: accesibilidad práctica — focus visible, aria-labels, navegación por teclado, contraste; mobile-first responsive.
75–110Práctica maestro-alumno: parejas rediseñan su landing React con Tailwind + 3 componentes shadcn; evaluan accesibilidad con Lighthouse.
110–135Reto individual: modal de "Solicitar asesoría" con Dialog de Radix + validación visual.
135–140Cierre: entrega E6 (deploy con score Lighthouse ≥90).
Evidencia E6: UI rediseñada responsive + captura Lighthouse + evidencia de navegación por teclado. XP: 200
Sesión 7 · Datos y API · Enrutado, fetch y validación · El orientador se conecta140 min
Aprendizaje esperado: React Router / TanStack Router, consumo de API REST, esquemas de validación (zod), manejo de loading/error states, server functions (concepto client vs server). Reto: "Consumo real" — conectar la UI a datos externos (JSON propio, JSONPlaceholder, o API pública) con estados de carga.
0–15Inicio: ¿cliente o servidor? Mini-diagrama del flujo del orientador real (browser → /api/orientador → gateway).
15–50CodeAlong: rutas (/ , /servicios, /contacto) con router, layout compartido, rutas 404; fetch con loading/error/empty states.
50–80CodeAlong: validación con zod (validar payload de contacto y respuesta de API), funciones de utilidad puras, manejo de errores amigables.
80–115Práctica maestro-alumno: trios conectan su app a un "backend simulado" (archivo JSON o API pública). Deben implementar estados de carga y error reales.
115–135Reto individual: formulario "Solicitar asesoría" que valida con zod y simula envío (fetch a jsonplaceholder.typicode.com o endpoint propio).
135–140Cierre: entrega E7.
Evidencia E7: App con ≥3 rutas, datos dinámicos, validación zod y manejo de errores. XP: 200
Sesión 8 · IA generativa + pruebas + deploy · Demo Day · Tu mini SaaS150 min
Aprendizaje esperado: Consumo de IA generativa (chat streaming, prompts de sistema, límites y guardrails), pruebas unitarias con Vitest, despliegue y documentación. Reto final: "Demo Day" — cada alumno presenta su mini aplicación completa (landing + asistente IA + WhatsApp + pruebas) en 5 min.
0–20Inicio: análisis del orientador.server.ts real: system prompt, "solo datos confirmados", streaming, resumen estructurado. Discusión: ¿qué pasa si la IA inventa un precio?
20–55CodeAlong: integrar un chatbot con API (Lovable AI Gateway vía backend del curso, o Gemini/OpenAI free tier). Prompt de sistema con "datos confirmados" + fallback a WhatsApp.
55–80CodeAlong: Vitest — pruebas unitarias de funciones puras (builders de links, validaciones, transformadores), igual que whatsapp.test.ts/resumen.test.ts del sitio real. npm test.
80–115Práctica maestro-alumno + integración: parejas unen frontend+chatbot+whatsapp; escriben 3 pruebas unitarias que pasen.
115–140Deploy final (Vercel/Netlify/Lovable) + README con capturas + bitácora de aprendizajes.
140–150Demo Day: 5 min por equipo (demo + 2 min defensa con rúbrica). Entrega E8 + retro final.
Evidencia E8 (integradora): Mini aplicación desplegada: landing + chatbot IA restringido a datos confirmados + botón WhatsApp + pruebas unitarias + repo público. XP: 300 (jefe final)

3. Rúbricas (SEET)

Escala: 4 = Sobresaliente · 3 = Satisfactorio · 2 = En desarrollo · 1 = Insuficiente · 0 = No entregado. Calificación = promedio ponderado × 10. Se firma con el alumno al momento de la entrega.

Rúbrica general por evidencia (aplica a E1–E8)

#CriterioPesoIndicadores (4 / 3 / 2 / 1)
1Cumplimiento funcional35%La app hace todo lo pedido, sin errores en flujo principal / hace lo esencial con detalles menores / cumple parcialmente / no cumple lo central.
2Calidad técnica25%Código limpio, legible, organizado en archivos, sin errores de consola ni de compilación / ordenado con detalles menores / funciona pero desordenado / errores graves.
3Diseño y UX20%Responsive, accesible (teclado/aria), coherente visualmente / responsive con detalles / estático y rígido / sin cuidado visual.
4Entrega y documentación10%URL pública + repo + README completo + commits descriptivos / entregado con README básico / incompleto / solo código.
5Innovación y esfuerzo10%Reto extra resuelto o función creativa propia / intento de extra sin completar / lo mínimo pedido / copia sin adaptar.

4. Dinámicas maestro-alumno (cómo se corre cada sesión)

MomentoDinámicaRegla de oro
Inicio (10 min)Quiz relámpago / "rompe algo en vivo" / lluvia de ideas. Se proyecta el reto del sitio real como motivación.Todos los alumnos en el mismo commit inicial del repo del curso.
CodeAlong (30–45 min)El maestro programa en vivo proyectado; los alumnos replican en paralelo. Se detiene cada ~10 min para verificar.Nadie avanza si el maestro no confirma "checkpoint" (todos en verde).
Práctica (30–45 min)Driver/Navigator: parejas o tríos rotan cada 10 min. En tríos hay roles: constructor, revisor de rúbrica, documentador.El revisor usa la rúbrica como checklist en vivo; el documentador toma notas para el README.
Reto (10–20 min)Desafío individual con tiempo límite, entrega al Drive/repo del curso. Los 3 mejores pasan a "Reto Bonus".El reto nunca repite lo del CodeAlong; siempre es una variación.
Cierre (10–15 min)"2 estrellas y 1 deseo": cada alumno dice qué aprendió y qué quiere mejorar. Se registra XP y se entrega la minuta de la evidencia.La evidencia se entrega en la misma sesión o 48 h después (según rúbrica).
Reglas de clase (leer el primer día):
1. El código se trabaja en el repo del curso; nada de "me lo mandaron por WhatsApp".
2. Copiar está permitido solo como punto de partida: la rúbrica penaliza entregas idénticas a las del maestro.
3. El error es información: cada bug resuelto suma XP extra (5 pts c/u, máx. 20/sesión).
4. Asistencia mínima 80%; las sesiones son presenciales con equipo propio (o en el aula de cómputo).
